## 两项修复及复核结果

### R-1：Flow 跨多个 Capability 的关系（已解决；初次 Medium）

- 原始依据：原文 L69 原则 6 明确“一个 Task 可以支撑多个 Flow；一个 Flow 可以跨多个 Capability”。
- 初次发现：PRD FR-4 仅保留 Task↔Flow 多对多与共享依赖，未显式保留 Flow↔Capability 的跨能力组合。
- 修复复核：FR-4 现明确“允许一条 Flow 跨多个 Capability，也允许 Task 与 Flow 多对多”；addendum“四部分的阶段完整性”结尾同步保留跨能力与共享能力引用。Requirement 单一覆盖归属仍独立保留。该项已解决。
- 初次缺口的风险：下游仍可能把 Flow 设计为单一 Capability 的子对象，进而被迫复制同一 Flow 或共享定义，违背已确认的组合边界。这不是要求特定 schema 或新增功能。
- 初次修复建议（现已落实）：在 FR-4 多对多句旁明确“一个 Flow 可以组合多个 Capability；共享能力通过受治理引用复用”，保留 Requirement 单一覆盖归属与共享依赖分离的现有表述。

### R-2：四部分在 Task 拆分前的最低语义内容（已解决；初次 Medium）

- 原始依据：原文 L145–150 的阶段表要求 Task 拆分前明确领域结果、前后条件、状态所有者、允许动作、关键不变量和失败行为；适配的输入提交／状态读取／反馈职责；逻辑控件到命令／视图状态及主要交接；场景进入退出、必要视图／视觉资源／布局职责。L467 要求 PRD 说明四部分约束行为和检查结果，而非固定字段编码。
- 初次发现：FR-4／FR-7 保留可机器读取与分阶段细化，但遗漏四部分拆 Task 前的具体行为级最低内容，尤其领域允许动作、关键不变量、前后条件和失败行为。
- 修复复核：addendum 新增“四部分的阶段完整性”表，完整恢复四部分在拆 Task 前、Chapter 6 前的分层内容；FR-4 明确引用该表。表中没有固定 JSON 字段、类名、节点路径，不要求前置实现；Flow 完整、Task 可部分适用、planned 与真实对象后检查的边界均保留。该项已解决。
- 初次缺口的风险：可能出现只有四部分标签／负责人和交接边的规划也获采纳，领域行为和适配反馈仍等到 Task 稳定后才发现缺口，削弱本次前移的目的。
- 初次修复建议（现已落实）：在 FR-4／FR-7 或 addendum 增加短小的分阶段四部分表，恢复原文行为级最低内容；不指定 JSON 字段、类名或节点路径，不要求算法／视觉制作提前完成。PRD 主文只需一句明确引用补充表作为采纳完整性要求。
