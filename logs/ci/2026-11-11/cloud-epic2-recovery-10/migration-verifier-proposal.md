## Problem and reviewed choice

The existing historical host deliberately requires an installed original R56/R52 owner, original interpreter/command identities, actual fixed Windows source paths and the original target's physical identity. The migrated null authority was deliberately excluded from the original machine's populated uncommitted installation. Filling it with cloud facts would not make the unchanged old verifier accept this copied target. A different Windows executor alone is also insufficient: physical target IDs, source paths and old interpreter/policy predicates remain.

The old worker also requires Windows Job ownership before any project code is released. There is no demonstrated delegated equivalent in the present Linux executor; cgroup is mounted read-only. A generic Linux process backend would not solve the historical identity mismatch.

Clean Astra max review supports the narrower proposal: a new, explicitly versioned, read-only migration DATA verifier for this one history. It executes current trusted validation code, never imports/executes archived source or releases an old owner/native/model/driver worker. Removing old worker execution does not by itself satisfy its authentication duties. Any eventual authenticating consumer must preserve those actual duties with independently supported evidence and explicitly distinguish its own execution. A data-only checker needs no authority change; an authenticating replacement is not installed here.
