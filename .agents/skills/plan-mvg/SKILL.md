# Plan MVG

## Role

Design cumulative player-journey integration coverage after Capability planning. This Skill is independently callable and consumes one explicit Capability file/version. It does not run or modify `plan-capabilities`.

## Boundaries

- GDD and reviewed Requirements remain semantic authority; Capability is a derived navigation index.
- Require an explicit Capability path and explicit target manifest path. Never select “latest” implicitly.
- A flow may span many Capabilities; a Capability may participate in many flows. Do not mechanically create one flow per Capability.
- Generate journeys from the explicitly selected Capability version, then identify observable cross-Capability/system boundaries. Task IDs supply ownership, Acceptance, contract and test evidence only; Task enumeration must not create runtime API obligations. Test/governance Tasks remain evidence-only even when referenced by legacy handoffs. Data-only contracts are not executable entrypoints.
- Preserve source-named sending/receiving systems and map their real task owners, including shared ownership. Assert the same interaction in flows, entrypoints and planned tests; task labels alone do not establish a system boundary.
- Real task IDs, owners, contracts and existing tests must be verified from repository inputs. Missing objects become gaps; never invent them.
- Planned entrypoints may target not-yet-created implementation paths only when a real owner task, target symbol/path, inputs/state/assertions and implementation acceptance are explicit.
- Existing verified entrypoints must point to files that exist now.
- `implemented` means a test implementation exists. This Skill never writes `passed` or `runtime_verified`.
- `coverage.blocking_task_ids` comes from the prepared Taskmaster master table, including the existing dedicated integration-owner exclusion. Planned entrypoints/tests and absent runtime evidence never change task status or invent task blockers. Dotnet selectors are class names, not filter expressions.
- Reserve `gaps` for unresolved upstream semantics, real owners, Acceptance or required real contracts. Valid planned entrypoints/tests and absent runtime evidence are implementation/manual obligations, not upstream gaps. Preserve them as planned and document their boundary; never disguise a genuine gap to approve a plan.
- Existing cumulative flows/tests remain unless a reviewed specification explicitly authorizes update/retire/coverage weakening. The same guarded `update_mvg_baseline.py` contract is used for apply.

## Primary workflow

### Capability append generation (current default)

新 `generate` 使用 `capability-local-selection.v1`，按冻结 Capability 顺序逐项执行。当前项的三个独立候选从相同的已接受累计 seed 生成增量，包含 flows、新 Requirement 记账、entrypoints、tests 与有来源依据的累计变更说明。每项恰好三个增量准入后才比较排名；选定增量成为下一项唯一 seed。累计基线只读，不作为第四候选或 fallback。跨 Capability 的 flow 可以扩展，不能弱化已接受 outcome、映射、handoff 或测试。共享 Requirement 只记账一次，同时保留参与上下文。

Before accepting an increment, run deterministic reference/membership/coverage/cumulative-delta checks and a fresh independent semantic hard check of that Capability and every affected cross-Capability flow/handoff. Preserve complete selected Requirement, source-block and Acceptance text. Accepted predecessors are visible to the next Capability.

Use complete inline input when the fully wrapped request fits. When auxiliary reference files make it too large, send every file in full through bounded, fresh isolated evidence-inspection calls. Each inspection also receives the complete core authority and scope. Oversized individual files are partitioned into contiguous character ranges; exact ordered reassembly, file/content/part hashes, all-part output accounting, line-address citations and request/receipt identities are machine checked. Preflight every batch before the first inspection. Generation receives complete core authority plus every inspection report and the full referenced-evidence inventory. The synthesis view may losslessly de-duplicate repeated task-view fields and avoid repeating citation source lines already bound to immutable parts; the complete rows, source bodies, repository-wide path index and resolved citation lines remain in the hash-bound transport proof. The path index is local discovery metadata, not source content; prepared-reference and proposal-path checks remain authoritative. Semantic admission independently reinspects the full auxiliary text against the actual proposal; it cannot use generation inspectors as approval evidence, and a source-backed hard conflict cannot be overridden by the main reviewer. This is complete source delivery across independent contexts, not pagination that pretends cumulative context has no limit, and not raw full-file delivery to the main synthesis call. Share duplicate JSON-schema domains through `$defs` without weakening validation. If complete core authority or all inspection results still cannot fit, stop rather than clip or summarize them away.

Inspection calls count toward the same 64-call lineage budget. Reuse a completed inspection only inside this candidate and clean Capability context, with exactly matching immutable sources, accepted base and (for review) proposal. A fresh page click or clean restart cannot consume prior-context inspections. Persist full text, ranges, outputs and receipts under `capability-append/`; admission recovery verifies the full independent review transport.

Inspection citations use CLI-enforced 1-based line addresses within the exact source part. The transport adds compact line labels while retaining every original character, including line endings and trailing whitespace. Resolve citations deterministically from the immutable part; synthesis receives the exact addresses and derived facts, while the complete source and resolved citation text remain in the transport proof. The model never supplies purported verbatim quote text. Schema sharing retains each part's exact address bounds.

Repair one stable hard issue at a time, at most three attempts per issue. Reject collateral changes or new deterministic/semantic defects atomically. After three failures restart the same Capability from immutable prepared inputs and accepted predecessors only. Never pass failed proposals, findings, prompts, segments or workspaces into the new context, and never skip the Capability. Generation, repairs and Capability semantic checks share a durable 64-model-call budget per candidate lineage; slice restarts do not reset it. At exhaustion retire the entire candidate batch and do not automatically grant another 64-call batch.

每项准入不足三个时写入 `selection_blocked_insufficient_admitted_candidates`，保留此前已选前缀与当前候选证据，不推进下一项。排名仅比较三个已准入增量，落选只能因为排名。完成全部项后执行完整机器与累计 delta 校验，不追加整批语义硬审查。最终 `review`、`validate` 本地重验混合 winner chain 的每项独立准入 proof/receipt。页面新点击始终创建新 run；旧 run 只按其已记录策略恢复。

逐项迁移的范围说明：Story 2.1 提供选择和前缀证据；Story 2.2 为 selected 增量准备不可变 checkpoint bundle，事务身份绑定 schema/run/Capability/order/base/proposal/selection receipt 的 canonical tuple。bundle 存在只代表 prepared；只有 `run.json` 一次原子提交 checkpoint 指针、selected 前缀和 accepted hash 后才可作为下一项 seed，写失败或 stale base 不推进。完整幂等 replay 与身份冲突仍属于 Story 2.3。历史整批策略及 incumbent D 仅用于显式旧 run 恢复，不用于新 run。

### Stage entrypoints (segmented generation details describe legacy recovery)

1. Prepare the exact input identity:
   `py -3 scripts/python/plan_mvg.py prepare --run-id <id> --capabilities docs/planning/semantic-topology/capabilities.v1.json --manifest docs/testing/mvg/<manifest>.json --task-id <id> [...]`
2. Include every actual task sink of the current source round. Prepare derives the round from added/changed ledger sources (all sources for a cumulative re-plan with no delta), checks active delivery Requirements and legitimate non-task sinks, and requires current Chapter 5 evidence. An omitted task blocks even when every supplied task is ready. `--allow-unready-draft` is for gap inspection only.
   When `--manifest` points to an existing manifest, its coverage scope is frozen at prepare: required flow IDs, Requirements, Tasks, tests, source paths and contract refs are the cumulative target. A pilot manifest does not expand into full-project coverage; out-of-scope model output is rejected deterministically.
   Explicit per-flow `requirement_ids` and `capability_refs` define that flow's semantic boundary, including explicit empty lists. Only missing fields are inferred from that legacy flow's task views. Evidence-owner tasks never expand an explicit boundary with unrelated governance Requirements. Retain baseline tests and handoff bindings. Missing verification may add `planned` tests within the same journey using schema-bound `verify-<flow-id>-<name>` IDs, real owners, Requirement membership, explicit handoff indexes, inputs, assertions and implementation acceptance. It cannot retire or relabel old tests, expand Requirement scope or claim runtime verification. Source-backed handoff corrections still require cumulative delta authority and independent admission.
   Prepare copies existing baseline flow/contract/test dependencies and task refs. It also writes immutable `coverage-skeleton.json` and an intentionally empty `entrypoint-skeleton.json`; the coverage skeleton contains every active delivery Requirement and is non-droppable, while entrypoints are later derived from Capability flow boundaries rather than Task placeholders. Add any other existing implementation, test, verification or reviewed authority with repeated `--evidence-ref <repo-file>`. Every claimed existing dependency must be readable in this fixed bundle and remain unchanged through apply. If a new dependency was omitted, prepare a new run with that explicit ref; never bind fresh evidence after review. Not-yet-created planned paths remain implementation obligations.
3. 为每个 Capability 生成、准入并评选三个独立增量：
   `py -3 scripts/python/plan_mvg.py generate --run-id <id> --llm-backend codex-cli`
   The exact `capabilities.v1.json` supplied to `prepare` is the sole Capability SSoT. GDD, task views, contracts, tests and an existing MVG manifest are auxiliary evidence and cannot create or reassign Capability membership. Generation creates `candidate-1`, `candidate-2`, and `candidate-3`; each candidate has its own prepared bundle, workspace and fresh isolated model context. Bounded sections (flows, coverage, entrypoints and tests) are merged only inside that candidate. Each candidate starts with one fresh generation invocation. A hard issue is then repaired serially in a fresh bounded attempt; after three attempts for the same issue the lineage is retired and a clean replacement is created from immutable prepared inputs. Runner-level output-schema enforcement and local identity/routing/reference/full-proposal validators remain mandatory.
   每个增量在评选前通过机器、累计 delta 与独立语义准入。稳定硬问题按顺序最多修复三次；退役后从不可变输入与已选前缀创建干净上下文，不读取失败产物。lineage 仍受 64 次调用止损约束，拆分 Capability 不得静默扩大预算；runner/schema 故障属于执行失败。三个已准入增量的 selector 行都为 `viable`，只按比较排名选择，不引入 incumbent D。评选输入绑定 Capability/order/base、candidate lineage 及 proposal/proof/receipt hash。最终选定链写入根 `proposal.json`，所有候选与逐项选择证据保留在 run 目录。

   以下整批 routing/segment 说明仅适用于显式旧策略恢复；新逐项路径使用 Capability append schema 和逐项 proof，不绕过完整来源及累计校验。
   Each candidate first generates its own complete Requirement routing table through the isolated model runner. The CLI schema and local gate require exactly one disposition per Requirement: `flow`, `other_verification`, `deferred`, or `source_gap`. Task ownership bounds supporting evidence; it never assigns semantic routes automatically. Shared Capability context does not grant coverage ownership: `flow.requirement_ids` remains an exclusive coverage claim. A non-runtime Requirement without a prepared legitimate sink or reviewed deferral remains a blocking `source_gap`; never fabricate a runtime test, sink, or authority.
   Segment routing is enforced before model output is merged: a frozen flow request and its handoffs use that flow's incumbent test IDs, and its test request uses the same exact flow/test domain in the CLI output schema, inline prompt and local routing validator. Complete the cumulative baseline projection at the flow barrier, then generate coverage, entrypoints and tests from those final flow rows. The global manifest ID set is an accounting boundary, not a segment's permitted output domain. An empty frozen test domain permits no test rows. For a new manifest, generated flow/test IDs are prefix-constrained and tests may reference only the actual flows from their routed scope. These rules apply to fresh responses and reused segments; prompt instructions do not substitute for CLI enforcement.
   Repair uses a temporary proposal bound to the current proposal hash and the current issue's explicit row/field/dependency scope. Accept atomically only when the current issue is reduced and no new deterministic errors appear; other pre-existing issues may remain. Reject unrelated edits and preserve the last accepted proposal and valid segments. Rejected patches cannot become later seeds or caches. A supported routing change rebuilds dependent sections and invalidates the old semantic proof. Internal correction calls count toward the same three-attempt issue limit and the hard 64-invocation lineage budget; no repair overflow is allowed. Retired slots start clean replacements immediately rather than waiting for sibling candidates.
   Coverage segment `authority_ref` and `verification_ref` fields are limited to immutable prepared source/reference paths (optionally with anchors) by the CLI schema and the segment reference gate. A Requirement ID is not a file reference. Invalid coverage references trigger bounded section correction before candidate merge; deferred coverage still requires reviewed authority and independent semantic approval.
   Frozen flow segments also return `change_reviews` under the CLI schema. A changed incumbent outcome, Requirement membership or Capability membership needs a review for that exact flow ID with prepared specification authority and a source-backed rationale; unchanged fields use an empty array. Missing, duplicate, foreign-flow, unreviewed or unprepared justifications retry the segment before merge. Repaired flow sections replace stale justifications. These model-authored proposal justifications never substitute for cumulative delta validation or independent semantic admission.
4. Verify the selected proposal's existing admission evidence locally by its hash-bound proof and bounded immutable inputs:
   `py -3 scripts/python/plan_mvg.py review --run-id <id> --runner scripts/python/openai_isolated_model_runner.py`
   The runner argument is retained for compatibility with older/unbound runs; a current run must already contain the admission proof and its execution receipt. Comparative selection persists a `selection-receipt.json` and recovery requires its exact input/output hashes, workspace-only fresh-session runner description, and matching no-tools model receipt. The projection retains source context and hash-bound excerpts of referenced evidence; it is not a full code review or runtime proof. Deterministic validation continues to use the complete prepared bundle. This stage verifies hash-bound admission evidence; it cannot switch to another ranked candidate or introduce a new semantic veto after selection.
5. Deterministically validate complete Requirement-to-flow/other-verification/reviewed-deferral accounting, real task/Capability membership and executable boundary evidence for each handoff flow, and the original initial manifest or cumulative delta. Do not require one entrypoint per Task. The entrypoint skeleton is intentionally empty; entrypoint requests are routed by Capability journeys with handoffs/source paths, and the independent reviewer checks actual runtime boundary completeness:
   `py -3 scripts/python/plan_mvg.py validate --run-id <id>`
6. Apply only after independent review and validation. Source, task master/views, Acceptance, referenced contracts/tests/ADRs, Chapter 5 evidence and original manifest identities must still match prepare:
   `py -3 scripts/python/plan_mvg.py apply --run-id <id> --confirm`
7. Resolve final obligation bindings before Chapter 6. Keep current milestone change plans under `docs/planning/milestones/`. For each actual milestone owner, rebuild the existing Chapter 5→6 handoff against current readiness and the applied MVG manifest:
   `py -3 scripts/python/plan_mvg.py rebind-handoff --run-id <id> --task-id <task> --change-plan <reviewed-plan.json> --out <handoff.json>`
   For an ordinary task, verify applicability and bind its current Chapter 5 readiness without creating a milestone handoff:
   `py -3 scripts/python/plan_mvg.py rebind-handoff --run-id <id> --task-id <task>`
   This ordinary route fails closed if an applicable milestone plan exists.

For an existing manifest, the Skill computes a reviewed delta and passes it through `update_mvg_baseline.py` logic; it does not overwrite the old baseline directly. For a first manifest, it validates the same runner schema before creation.

## Evidence and handoff

The durable run is under `logs/ci/mvg-planning/<run-id>/`. The applied trace sidecar is under `docs/testing/mvg/planning/<run-id>.json`; it is planning provenance, not another runtime-test state authority.

The applied trace records per-task obligation bindings and is consumed by both `chapter6-route` and the single-task lane. Omitting `--milestone-handoff` cannot bypass pending obligations. A milestone handoff itself binds the baseline manifest hash; later manifest/readiness/plan changes invalidate the binding. Ordinary bindings use current Chapter 5 readiness and create no synthetic milestone handoff. Planning and rebind keep `runtime_verified=false`; runtime evidence belongs to the MVG runner/Chapter 6 acceptance path.

Use the MVG runner's newline-normalized content hash for committed manifests, milestone plans and milestone handoffs. Git LF/CRLF conversion preserves those bindings; content edits invalidate them. Keep prepared authority snapshots, readiness and interrupted-apply journal checks byte-exact.

## Refresh rules

Task status or small reference edits do not automatically regenerate Capability or MVG planning. A new code revision invalidates runtime evidence when appropriate, not the planning manifest by itself. Capability rename/regrouping triggers MVG reference/behavior impact review, not automatic wholesale flow regeneration.

Never prepare over an existing run ID: resume its incomplete stage, or choose a new ID for changed source inputs. Deltas are computed against the prepared manifest copy, never silently rebased onto a later manifest.

Apply also journals the approved trace and manifest together. Re-running the same apply recovers interruption and preserves subsequent legitimate obligation bindings. Independent review execution has at most ten persisted fresh invocations per run; candidate admission gives each hard issue a separate three-repair limit. Transport, identity, and JSON/runner failures may retry and persist an `error_type`, but are never converted into semantic findings. Re-running an already valid review reuses its evidence. Review inputs are supplied through the bounded review workspace/evidence projection so transport limits do not turn an oversized input bundle into a semantic verdict; referenced evidence excerpts retain a larger head/tail window and file hashes, while the complete immutable prepared bundle remains the deterministic validation authority. The projection runs deterministic preflight before the first model call and adaptively shrinks excerpts when needed; input-size or preparation failures create no Review attempt and do not consume the ten-attempt budget. The final review verifies the selected candidate's hash-bound admission proof and never replaces it.

Each fixed proposal has a hash-bound `semantic-review-publication-<proposal-sha256>.json` checkpoint containing its verdict and execution receipt. Re-run review to finish interrupted publication without another invocation. Before that checkpoint exists, require the completed attempt's original output hash, runner/analysis identities and receipt to match before reuse. Unknown target edits or corrupt checkpoints block recovery. Completed records preserve earlier blocked verdicts when a repaired proposal is reviewed within the same ten-attempt limit. Finish any pending publication against its original proposal before revision. Drafts and invalid semantic accounting never gain formal approval by replaying publication.

Generation execution has three admitted candidate slots, with fresh lineage contexts and a separate three-repair budget for each hard issue. A candidate's sections run in its own ephemeral workspace using the selected backend's environment-default model configuration; Windows timeout cleanup terminates the complete child process tree. Retired lineages are replaced from immutable prepared inputs and never share retired prompts, findings, proposals, or segments. Selection has a bounded transport/schema budget and never receives blocked candidates. The independent semantic Review verifies the selected candidate's hash-bound admission evidence; it cannot replace the winner. Identity/transport failures remain execution failures and do not create semantic findings or regenerate Capability.
