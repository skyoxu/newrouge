- Chapter 5 v3 root cause: the class-specific acceptance Locator call itself can omit the true task source before adapter attribution. The earlier acceptance supplement mixed `GM-0128`, `task 28`, and generic `acceptance/test/refs`; in the real repository this creates enough high-scoring referencing documents to exhaust the Locator's consumer-level candidate window. Adapter-side attribution ordering cannot recover a candidate that the Locator never returned. Numeric `task 28` also has weaker lexical precision than the view id because substring-oriented token matching can match paths such as task 128.
- Chapter 5 third repair: acceptance retrieval is now task-identity-first. Policy removes generic `acceptance/test/refs` retrieval terms and declares `task-view-first`; `prepare_knowledge_context.py` therefore uses a specific `GM-/NG-` view identifier when present and falls back to `task N` only when no view id is available. The Locator now also gives a deterministic `TASK_IDENTITY_BONUS` to `.taskmaster/tasks/*.json` modules whose returned location is the exact requested task identity. `rank_evidence` records `task_identity_match` and `task_identity_bonus`. This makes the defining task source rank above documents that merely reference the same id while preserving the existing threshold and stable ordering.
