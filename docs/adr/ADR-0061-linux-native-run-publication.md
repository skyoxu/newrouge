# ADR-0061: Bounded Linux publication for native planning runs

- Status: Accepted implementation scope; real native and Windows whole-Epic acceptance remain evidence-dependent
- Date: 2026-11-12
- Scope: The initial run-directory publication in the existing Story2.9 producer; no new planning lifecycle
- Authority: Continuing Epic2 authorization and the explicitly requested clean Astra max necessity/proportionality assessment in continuation25

Story2.9 requires genuine complete-item proof, original coordinator ownership, immutable accounting and epoch/reopen behavior. Its original ACs do not require every independent planning step to execute on Windows. AR17 and Story2.8AC5/2.10AC6 retain their Windows delivery/acceptance scope. The existing formal entrypoints have no synchronous fresh-producer alternative; a test invoke_factory, manual run.json or old m4 relabeling is not a substitute.

Keep exclusive staging, complete initialization files, validation and the existing coordinator/operation locks. Preserve Windows os.rename behavior. On Linux, publish with the kernel's atomic RENAME_NOREPLACE operation; reject an unavailable primitive or unsupported filesystem without an ordinary rename, replace or copy fallback. Existing empty/nonempty/file destinations remain untouched, and failed staging remains evidence. The primitive's no-replacement semantics are documented in the [Linux manual](https://man7.org/linux/man-pages/man2/rename.2.html).

This is a narrow validation-host extension, not an assertion that Linux worker fault handling equals Windows Job Objects. Normal Linux producer evidence remains host-specific. Missing outcome, unconfirmed cleanup or unknown dispatch stops the original run with its occupied calls and retained artifacts. Do not add a generic Linux lifecycle system as a new Story2.9 gate. Windows process/fault acceptance remains separately identified; the four previously passed controls still have synthetic upstream admission.

The production change invalidates the earlier audit's current transitive-tool identity. Preserve its genuine completed2 calls, full outputs, original limit2 and source epoch. Only a separately recorded fresh current audit may qualify changed-source3B preparation; it cannot reset or re-sign the old audit. Any new allowance is explicit and additive, counted only as permits are actually reserved. Do not spend further reviews while necessary current input capacity is unresolved.

The5 targeted Linux controls use real kernel directory publication and competing processes, with explicitly synthetic storage payloads. They verify no replacement, complete winner/retained loser, staging/postpublication interruption and unsupported-primitive refusal; they confer no model/adoption qualification. No domain schema, registry, authorization object, CLI stage or resource threshold changes.
