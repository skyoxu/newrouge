# ADR-0045：B 路线宿主取消与清理诊断

状态：拟议实现；离线控制待 Root 执行。

范围：Story 2.5 第 2 轮审核，R2-B8 与 R2-B9。本决策不授予原生资格、准入、
服务提供方身份、重试、退款或额外预算。

## 问题

Windows 的一次 `CancelSynchronousIo` 可能发生在一次成功读取之后、下一次阻塞读取
之前。仅取消 I/O 不等于请求停止。此外，App Server 的清理异常可能替换真正的协议
异常或超时异常，并阻止后续独立清理阶段得到尝试。

## 决策

合并输出的 runner 读取器拥有一个停止事件。每次 `read1` 前检查该事件，始终保留
每次已完成读取的原始字节，并且只由读取器自己关闭流。`_stop_owned_pipe_workers`
先发布停止请求，再重复取消已有记录中的工作线程 I/O 并进行短时 join，直到这些
线程确认退出，或单个 0.5 秒清理窗口到期。取消失败后仍尝试退出握手，并报告失败。
不取消外部线程或进程。现有进程终止边界及后续进程等待保持不变。

App Server 使用相同的有界工作线程握手。其 stderr 读取器在下一次读取前检查停止
请求。协调器独立尝试进程终止、管道停止、每个安全的流关闭、journal 关闭以及实际
stderr 保存。只要任一已记录工作线程仍然活跃，就不关闭其缓冲流。如实报告停止
失败；不强制终止 Python 线程，也不抢占活跃线程持有的流锁。

协议 `try` 主体、重放与身份检查、high/no-tools 配置、模型请求、响应解释及原始
协议 journal 均保持不变。`sys.exc_info()` 将实际主异常传入独立清理逻辑。存在主
异常时，同一异常及其 traceback 继续传播，并附加明确标注为宿主诊断的 note。
没有主异常时，清理失败会抛出宿主失败，即使 turn 已完成也如此；绝不将清理失败
解释为模型成功。

## 诊断产物

仅在清理失败且存在原 journal 路径时，以排他新建方式写入辅助路径
`journal_path.with_suffix('.host-cleanup.json')`。JSON schema 标识为
`newrouge.codex-app-server-host-cleanup.v1`，字段包括 `source='host_cleanup'`、
`model_success=false`、`primary_error`（type/detail 或 null）以及 `failures`
（stage/type/detail 条目）。这是宿主诊断证据，不是服务提供方输出、协议消息、模型
回执或准入证明。它不会加入协议 journal，也不会混入实际 `.stderr.txt` 字节。
已有诊断绝不覆盖。诊断保存失败本身会附加到主异常或宿主异常的 note 中，已有文件
保持原样。部分写入的诊断不能授予权限。

新后缀比 `.stderr.txt` 更长；冻结 Windows 路径容量的调用方必须将其纳入检查。
不会为适应该后缀而静默改变路径、操作系统配置或预算。

## 验证与限制

8 个小型确定性离线控制覆盖：已完成读取之间的停止、遗漏取消的时间窗口、有界
未退出、取消错误后的 join、多个清理错误下原异常与原始 journal 及实际 stderr 的
保留、活跃工作线程存在时拒绝关闭流、协议完成后的清理失败，以及独立的 stderr
和诊断保存错误。这些控制仅已编写，尚非执行结果。Root 保留已有的真实 Windows
夹具子进程控制用于集成验证。

既有的 stdout 字节无界累积问题（R2-B7）延期处理。本变更不增加字节上限、模型
超时、重试、新进程、新读取线程、跨动作缓存、模型调用或协议成功捷径。它不能
保证操作系统 I/O 取消成功；有界失败仍会明确报告，已计费工作仍保持计费。现有
公共 `cleanup_after_error` 保持原异常与清理失败独立保留、部分字节证据保留的行为。
