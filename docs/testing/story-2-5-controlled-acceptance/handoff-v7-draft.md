# Reward handoff test

Each isolated test scenario has one fixed reward R, one process at a time, serial calls and an initially empty durable journal. Only the named injected crashes interrupt calls; storage otherwise succeeds. Restart preserves that scenario's journal. Scenarios never share a journal. Between harness calls, a live process makes no journal or UI changes.

The only durable records are Accepted(R) and MapReturnCommitted(R). Each append is atomic and durable. A return means a MapReturnCommitted(R) append; rendering restored map state is not another return. At every observed journal prefix, each record occurs at most once and a return record requires an earlier acceptance record. Existing records must never be appended again. Case prefixes are empty (neither record), pending (Accepted only) and committed (both in order). Prepare pending by crashing accept after its acceptance append; prepare committed by completing accept. Retain the resulting journal and restart before the target case call.

The external harness invokes accept(R, call_id) or resume(R, call_id) with a fresh call_id. It records CallStart, Crash, CallComplete, ObservationComplete, ForceTerminate, ProcessExited, StartProcess and ProcessStarted outside the process in a single sequence. CallComplete carries that call_id and an observable ui_state: Idle or MapReady. Every non-crashing call must produce exactly one CallComplete and allow the harness to finish the independent observations specified below within 10000 milliseconds of CallStart, measured by the harness's monotonic clock and including all recovery work. Missing, late, duplicate or wrong-call completion or missing/late observations fail the test. No eligibility condition postpones this deadline.

accept must append missing acceptance, append any missing return and expose MapReady before CallComplete. If either record already exists, retain it without another append. In particular, first acceptance must expose MapReady, not merely write the return record.

resume with acceptance must append any missing return and expose MapReady before CallComplete. resume without acceptance must append neither record and expose Idle before CallComplete. resume after a committed return must expose MapReady without another return append. Neither operation requires another user action to finish.

Crash tests inject one crash before or after each append that is actually reached, or immediately before CallComplete. A crash before completion ends that invocation with Crash and no CallComplete. A process crash after CallComplete does not undo that completed invocation. Run separate normal and post-completion-crash tests for all six cases: accept/empty, accept/pending, accept/committed, resume/empty, resume/pending, resume/committed. In each post-completion test, inject the crash as the very next harness action after ObservationComplete for that call_id, with no intervening call or action. Every restart, including case-prefix preparation, uses this exact procedure: if the process is live after successful ObservationComplete, ForceTerminate is the next harness action; if already crashed, issue no second kill. Observe ProcessExited, then StartProcess with the unchanged journal and observe ProcessStarted before any API call. All crash hooks force-terminate the process and record Crash. ForceTerminate or Crash to ProcessExited and StartProcess to ProcessStarted each have a 10000ms external-clock deadline; timeout fails the scenario. After the first injected crash, use that restart procedure, disable within-call fault hooks and invoke resume with a fresh call_id, requiring successful CallComplete and ObservationComplete. Then perform exactly two additional cycles: immediately after that resume ObservationComplete, ForceTerminate as the next harness action, observe ProcessExited, StartProcess with the same journal, observe ProcessStarted, invoke resume with a fresh call_id and verify CallComplete and ObservationComplete. Within-call injection stays disabled during these cycles; the scheduled between-call ForceTerminate still occurs. No graceful shutdown, journal reset, unconfirmed process overlap or alternative restart mechanism is used.

For each normal completion, the external harness must independently read the actual ui_state and complete durable journal within that same deadline. Check call identity, exact completion count, time, observed state, journal order and record counts; reported state or counts alone are insufficient. The reported ui_state must match the independently observed state. After CallComplete, the process must leave state and journal unchanged until the next harness call or injected crash. After all independent checks pass, record ObservationComplete with the same call_id within that same deadline. Finish this event before the next call or the specified post-completion crash hook. For a crashed invocation, verify its ordered journal prefix, absence of CallComplete and subsequent resume result. A deadline already missed remains a failure even if a later crash occurs. Cover normal acceptance, idle resume, pending recovery, committed restoration, repeated accept and repeated restart/resume.
