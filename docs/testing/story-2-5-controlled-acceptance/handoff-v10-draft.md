# Reward handoff test

Each separate test scenario receives its own newly provisioned empty journal J. Scenarios never share J. Provisioning a different journal at a test boundary is allowed; resetting the same J within a scenario is forbidden. Within each scenario, one process handles serial calls for fixed reward R. Resources are durable journal J and volatile map UI, owned by the reward controller. J starts empty and can only become [Commit(R)] by one atomic durable append. Commit grants R and logically returns to the map; rendering is not another grant/return. Existing J is immutable. Each process starts with Idle UI. Storage succeeds except for the two crash hooks below.

Flow entry is accept(R,id) or resume(R,id); its guard reads J. Execution of accept appends Commit only if absent; resume never writes. Finalization shows MapReady if J contains Commit, otherwise Idle, then emits one completion carrying that call's id and the displayed UI. Thus first/repeated accept shows MapReady, and resume restores MapReady or Idle after restart. No additional user action is required.

Every call has a fresh id. A non-crashing call must complete exactly once and allow the external harness to independently read actual UI and all of J within 10000ms of call start on its monotonic clock. Reads occur after completion and before another call/crash; UI/J remain unchanged during these reads. Check id, completion count, deadline, expected journal/UI and agreement with reported UI. Missing, duplicate, late or mismatched results fail; a later crash cannot erase failure.

The only injected within-call crashes are force-termination immediately before or after the missing append: no completion for that invocation; J respectively stays empty or contains one Commit. Confirm exit, start a new process with unchanged J, confirm startup, then invoke resume under the same completion/observation rule. Exit after termination and startup after start each have a separate 10000ms harness-clock deadline; timeout fails. For ordinary restart after successful observations, request normal shutdown and confirm exit before starting and confirming the new process; use the same two control deadlines. Normal shutdown is not an injected crash. Within a scenario, never overlap processes or reset its J. Separate tests cover two same-process accepts from empty, empty resume, committed resume after a successful accept/restart, and each crash/recovery from a fresh empty journal. Planning this Flow does not claim it ran.
