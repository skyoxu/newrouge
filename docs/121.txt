六、这次 bmad-build 到底发生了什么？

这里我认为原因已经可以非常明确地定位。

Architecture 的 Deferred 中有一项：

Implement and test the Chapter 6/review adapters that add --frozen-context, --impact-report, and --revision forwarding...

而 bmad-build 最终生成的 implementation spec 恰好叫：

KCP Impact Analysis Adapter Handoff

并把 intent 定义成：

Chapter 6 和 Review 尚不能接收或验证 frozen context、impact report 与 Git revision。

最关键的是它主动冻结了这个范围：

Never: 不实现完整 index/resolver/analyzer。

所以流程实际上是：

完整 Architecture
       |
       | bmad-build 选中了一个 deferred implementation item
       v
Adapter Handoff 子规格
       |
       v
实现
       |
       v
status: done

而不是：

完整 Architecture
       ↓
完整 KCP Impact Analysis implementation
所以这次不是主要的“代码写坏了”。

相反：

handoff 这部分代码是基本符合它自己的规格和 Architecture 边界的。

真正的问题是：

bmad-build 的 scope selection / implementation planning 偏了。

它把 Architecture 中一个后续集成项当成了这次要完成的 feature。

5.6 Sol high 看起来基本忠实执行了它得到的 frozen implementation spec；问题发生在实施规格生成阶段的任务选择，而不是后面的代码生成推理能力。
