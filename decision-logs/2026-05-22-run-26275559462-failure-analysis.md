- Context: `F:\\gitlog\\ci-logs7_unpacked\\2026-05-22\\ci-pipeline-summary.json` reports `.NET` `tests_failed` with zero failed test names. `dotnet-test-output.txt` shows the actual sequence: build succeeds, all 592 tests pass, then `The active test run was aborted. Unlike the earlier coverlet file-lock case, this output does not mention `XPlat code coverage` or the file-lock text, so `_is_retryable_coverlet_file_lock_abort()` returns false even though the payload is clearly a post-run infrastructure abort after a fully green test body. Because of that, the wrapper reports `tests_failed` instead of retrying the post-run abort once.
- Decision: Generalize retry detection in `scripts/python/run_dotnet.py` from the old narrow coverlet file-lock signature to a broader retryable post-run abort predicate. The broader predicate still includes the existing coverlet file-lock pattern, and additionally treats `test host crashed` aborts as retryable when the output shows `Results File:`, `Attachments:`, and a fully green test summary (`Passed! - Failed: 0`).
- Consequences: CI no longer reports a false red when the actual test body is fully green and the only failure happens during post-run teardown/host shutdown. The retry logic remains narrow enough to avoid re-running deterministic red tests because ordinary failing outputs still do not match the retryable post-run abort predicate.
- Recovery impact: Recovery remains entirely in the shared wrapper layer. The next run should either succeed after one retry or expose a new deterministic failure class if the abort recurs with different evidence.
